# 分布式购物车 KV Store (CRDT + 向量时钟)

> **课程：** 并行式分布式系统
> **姓名：** 徐诗尧 旷慧娴 周若冰 黄伊恬

## 1. 项目简介

本项目实现了一个基于 CRDT（无冲突复制数据类型）的分布式键值存储系统，用于模拟购物车的高可用服务。系统采用 Python 编写，
单进程多线程模拟三个副本节点（Phone, PC, Pad），实现了数据的自动同步、并发修改冲突解决以及多种网络故障的容错。

## 2. 核心设计与特性

*   **Add-Wins OR-Set (CRDT)**：采用基于 Tag 的 OR-Set，保证了在网络分区时，并发添加和删除操作最终能够自动收敛，无
*   需加锁。
*   **向量时钟 (Vector Clock)**：用于追踪节点间的因果关系，解决物理时钟回退（如时钟回拨）导致的问题，正确判断并发冲突。
*   **幂等性保证**：引入 `request_id`，节点记录 `processed_requests`，完美解决“响应丢失导致客户端重试”时的重复写入问
*   题。
*   **原子落盘**：使用 `tempfile` + `os.replace` 实现持久化，确保节点宕机时 JSON 文件不会损坏。
*   **多线程安全**：内部使用 `RLock` 保护共享状态，解决高并发下的数据竞争问题。

## 3. 目录结构

*   `store.py`：系统核心代码，包含虚拟网络、KV 节点、CRDT 实现及所有测试用例。

## 5. 故障场景覆盖说明

本项目设计并测试了以下 9 个极端的分布式故障场景：

1.  **副本突然宕机**：存活节点继续服务，宕机节点重启后从磁盘恢复并同步。
2.  **网络分区+消息重复**：验证 CRDT 的幂等性，以及并发添加不丢失。
3.  **消息延迟乱序**：验证向量时钟在乱序到达时的因果正确性。
4.  **重启丢失内存**：验证本地持久化机制。
5.  **迁移中途宕机**：验证已落盘数据保留，未迁移部分可通过网络补齐。
6.  **热点 Key 高并发**：模拟 40 个线程并发写同一个购物车，无锁设计保证性能。
7.  **并发 CAS 冲突**：对比传统 CAS 机制，突出 CRDT 在并发下的优势。
8.  **系统时间回退**：注入虚拟时钟回退，验证向量时钟不依赖物理时间。
9.  **磁盘成功响应丢失**：验证重试机制不会产生多个商品 Tag。

## 6. 设计中的踩坑与思考

在设计这个任务中，结合这门课的内容，我想以下问题可以代表我的思考：

**1）为什么非要用 CRDT（无冲突复制数据类型），而不是直接用 Redis 那种分布式锁（或者CAS）？**
an:一开始我想的是用CAS来保证一致性。但在做测试7（并发CAS）的时候发现，两个客户端同时执行CAS，必定会有一个失败报错。购
物车这个场景，用户其实更看重“高可用”和“能用”。如果我在手机上删了个东西，电脑上刚好网络卡了一下，难道我就不能往购物车里
加东西了吗？CRDT 的 Add-Wins 策略非常好用，两端随便改，等网好了自动合并，并发也不会报错，非常适合购物车。

**2）为什么一定要用向量时钟？直接用物理时间戳（`time.time()`）不行吗？**
an:这是我做测试8（系统时间回退）踩到的坑。如果依赖物理时间，一旦服务器的 NTP 同步或者其他原因导致了时钟回拨（倒退一分
钟），那后发生的操作时间戳反而更小，因果关系就全乱套了。向量时钟虽然存的东西稍微多一点，但它能真正追踪出“谁依赖了谁”，
哪怕发生了系统时间回退，它也能准确判断出哪个操作是后来的。

**3）测试9（磁盘写成功，但响应丢失）里面，客户端重试了，为什么商品没有变成两份？**
an:这是我花了好久才搞定的问题。传统的重试如果服务端没做好幂等，就会产生脏数据（比如加了两次“苹果”）。我的解决思路是给
每个请求生成一个唯一的 `request_id`。节点里面维护了一个 `processed_requests` 字典。不管网络怎么重发，只要 ID 一样，
节点就直接返回上次缓存的响应，不再重新走添加逻辑。同时这个 ID 也顺便当成了 OR-Set 里面的唯一 Tag，一举两得。

**4）代码里那个 `_save_to_disk` 函数为什么写得那么长？还用了 `tempfile` 和 `os.replace`，直接 `open()` 写文件不
行吗？**
an:不行的。我一开始就是直接写文件的，结果在测试4和测试5（运行中途宕机）的时候，模拟节点突然 Crash。因为文件写到一半中
断了，重启的时候读出来的 JSON 是残缺的，直接导致程序崩溃（JSON Decode Error）。后来查了工业界的做法，必须用“原子写”。
就是先把数据完整写到一个临时文件里，确认落盘了，再瞬间替换掉原文件。这样哪怕刚写完的一瞬间断电，原文件也是完好的。

**5）在处理测试6（热点Key）的时候，是不是遇到了多线程报错？**
an:眉毛。Python 有 GIL 全局锁，一开始我以为不需要自己加锁。结果用 20 个线程同时去修改同一个购物车里的 CRDT 集合时，
疯狂报 `RuntimeError: dictionary changed size during iteration`。因为哪怕是单条指令，字典扩容的时候并发访问也会报
错。所以后来在节点读写和合并的地方，加了 `threading.RLock()`，虽然单机性能可能有一点点损耗，但保证并发绝对不会崩。

**6）你的落地持久化机制会不会影响性能？**
an：肯定会有影响，每次操作都要写磁盘，吞吐量绝对比不上纯内存。但这门课探讨的是特定业务负载和一致性要求，对购物车来说，
不丢数据比极致的速度更重要。如果真到了淘宝那个量级，我可能会结合预写日志或者缓存来优化。
