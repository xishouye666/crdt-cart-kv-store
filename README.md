> **姓名：** 徐诗尧 旷慧娴 周若冰 黄伊恬

## 1. 项目简介

本项目实现了一个基于 CRDT（无冲突复制数据类型）的分布式键值存储系统，用于模拟购物车的高可用服务。系统采用 Python 编写，单进程多线程模拟三个副本节点（Phone, PC, Pad），实现了数据的自动同步、并发修改冲突解决以及多种网络故障的容错。

## 2. 核心设计与特性

*   **Add-Wins OR-Set (CRDT)**：采用基于 Tag 的 OR-Set，保证了在网络分区时，并发添加和删除操作最终能够自动收敛，无需加锁。
*   **向量时钟 (Vector Clock)**：用于追踪节点间的因果关系，解决物理时钟回退（如时钟回拨）导致的问题，正确判断并发冲突。
*   **幂等性保证**：引入 `request_id`，节点记录 `processed_requests`，解决“响应丢失导致客户端重试”时的重复写入问题。
*   **原子落盘**：使用 `tempfile` + `os.replace` 实现持久化，确保节点宕机时 JSON 文件不会损坏。
*   **多线程安全**：内部使用 `RLock` 保护共享状态，解决高并发下的数据竞争问题。

## 3. 目录结构

## 5. 故障场景覆盖说明

本项目设计并测试了以下 9 个极端的分布式故障场景：

1.  **副本突然宕机**：存活节点继续服务，宕机节点重启后从磁盘恢复并同步。
2.  **网络分区+消息重复**：验证 CRDT 的幂等性，以及并发添加不丢失。
3.  **消息延迟乱序**：验证向量时钟在乱序到达时的因果正确性。
4.  **重启丢失内存**：验证本地持久化机制。
5.  **迁移中途宕机**：验证已落盘数据保留，未迁移部分可通过网络补齐。
6.  **热点 Key 高并发**：模拟 40 个线程并发写同一个购物车，无锁设计保证性能。
7.  **并发 CAS 冲突**：对比传统 CAS 机制，突出 CRDT 在并发下的优势。
8.  **系统时间回退**：注入虚拟时钟回退，验证向量时钟不依赖物理时间。
9.  **磁盘成功响应丢失**：验证重试机制不会产生多个商品 Tag。

## 6. 设计中遇到的问题及思考

在做这个任务设计过程中，结合我们这门课的内容，我想以下的问答可以表达我的思考：

**1）为什么不用分布式锁或者 CAS，而是要用相比操作更复杂的 CRDT？**
*   **回答：** 刚开始我用的是CAS。但在写测试7（并发CAS）的时候，我发现两个客户端同时去改，必定有一个会失败报错。其实购物车这种交互性项目最重要的是“用户体验”，但用CAS时手机上的删改可能会受电脑网络的影响，也就影响到了我们追求的用户体验。CRDT 的 Add-Wins 就可以解决这一问题，不论两端怎么改，等网好了它自己会合并，并发也不会报错，我觉得更好用。

**2）为什么一定要用向量时钟？直接用物理时间戳不行吗？**
*   **回答：** 刚开始我确实用的时间戳。结果在做测试8（时间回退）的时候发现：如果时间往回退了一分钟，后发生的操作时间戳反而变小了，因果关系会被打乱。也就是这种情况物理时钟靠不住。向量时钟虽然要记录的东西稍多，但它能准确判断出“谁先发生谁后发生”。

**3）测试9里磁盘写成功但响应丢了，客户端一重试，为什么商品没变成两份？**
*   **回答：** 这是我认为的一个难点。在分布式里，如果服务端没做好幂等（就是不管请求多少次，结果都一样），重试就会产生脏数据（比如加了两次“苹果”）。所以结合AI的建议，我给每个请求发一个类似身份证的`request_id`。节点记下处理过的 ID，只要重复发，就直接返回上次的结果。也就是说，只要 ID 一样，它就只认一次，顺便还把这个 ID 当成 CRDT 里的唯一标签。

**4）代码里那个 `_save_to_disk` 为什么写得那么复杂？直接 `open()` 写不行吗？**
*   **回答：** 不行的。直接`open()` 写的时候测试4和测试5（模拟宕机）的时候程序跑到一半突然 Crash。文件写到一半程序报错崩溃。后来在AI的帮助下我了解到“原子写”。我的理解就是先写个临时文件，等全写好了，再瞬间替换掉原文件。这样可以保证只要写好原来的文件就不会坏。

**5）做热点 Key 高并发测试时，遇到多线程报错了吗？**
*   **回答：** 是的。用 20 个线程同时去改购物车的时候，一直报 `RuntimeError: dictionary changed size`。py默认的锁无法完成多线程任务。然后我在读写的地方加了 `threading.RLock()`，用速度换稳定。

**6）每次都写磁盘，会不会影响性能？**
*   **回答：** 肯定会有影响，速度绝对比纯内存慢。我觉得这里就讲究权衡。对购物车这种业务，数据一致性比速度更重要。但我们的实验量级小，暂时可以承受。如果是大量级的任务我也问了AI，可以用预写日志（WAL）或者加缓存来优化性能。
```
